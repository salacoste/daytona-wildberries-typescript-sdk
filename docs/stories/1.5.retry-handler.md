## Story

**As a** SDK user,
**I want** automatic retries for transient failures,
**so that** temporary network issues or server errors don't break my integration.

## Acceptance Criteria

1. `RetryHandler` class with `executeWithRetry<T>()` generic method
2. Configurable retry settings: max retries (default 3), initial delay (default 1000ms), exponential backoff flag
3. Retries on: network errors, 5xx server errors, 429 rate limit errors
4. NO retries on: 4xx client errors except 429, authentication errors, validation errors
5. Exponential backoff calculates delay as `initialDelay * 2^attemptNumber` when enabled
6. Preserves and re-throws final error after max retries exhausted
7. BaseClient integration: wraps HTTP requests with retry logic
8. Unit tests validate retry logic, backoff calculation, and selective retry behavior
9. Integration tests simulate transient failures and validate successful recovery

### Architecture Overview

**RetryHandler Role:** Provides resilience against transient failures through automatic retry with exponential backoff

**Design Pattern:** Wrapper Function (Higher-Order Function)
- Wraps any async operation
- Generic type parameter preserves return type
- Transparent to callers (retry is invisible to API modules)

**Core Principle:** Fail-fast on permanent errors, retry on transient errors

[Source: architecture.md#Component 4: RetryHandler]

### Retry Policy

**Errors to Retry (Transient Failures):**

| Error Type | HTTP Status | Retry? | Reason |
|------------|-------------|--------|--------|
| RateLimitError | 429 | ✅ Yes | API limit temporarily exceeded |
| NetworkError | 500 | ✅ Yes | Internal server error (transient) |
| NetworkError | 502 | ✅ Yes | Bad gateway (transient) |
| NetworkError | 503 | ✅ Yes | Service unavailable (transient) |
| NetworkError | 504 | ✅ Yes | Gateway timeout (transient) |
| NetworkError | Timeout | ✅ Yes | Network timeout (transient) |
| NetworkError | No status | ✅ Yes | Network failure (transient) |

**Errors NOT to Retry (Permanent Failures):**

| Error Type | HTTP Status | Retry? | Reason |
|------------|-------------|--------|--------|
| AuthenticationError | 401, 403 | ❌ No | Invalid API key (won't fix with retry) |
| ValidationError | 400, 422 | ❌ No | Bad request data (won't fix with retry) |
| NetworkError | 404 | ❌ No | Resource not found (permanent) |
| NetworkError | 405 | ❌ No | Method not allowed (permanent) |
| NetworkError | Other 4xx | ❌ No | Client error (permanent) |

**Rationale:** Retrying permanent failures wastes time and resources. Only transient failures benefit from retry.

[Source: architecture.md#Error Handling Patterns]

### Exponential Backoff Algorithm

**Formula:** `delay = initialDelay * 2^attempt * jitter`

**Components:**
- **Base Delay**: configurable (default 1000ms)
- **Exponent**: 2^attempt grows exponentially
- **Jitter**: Random ±10% to prevent thundering herd
- **Max Cap**: 30 seconds to prevent excessive waits

**Example Timeline:**
```
Config: { retryDelay: 1000ms, exponentialBackoff: true, maxRetries: 3 }

Attempt 0 (initial): Execute immediately
  ↓ (fails)
Delay calculation: 1000 * 2^0 * jitter = ~1000ms
  ↓ (wait 1 second)
Attempt 1: Retry after 1s
  ↓ (fails)
Delay calculation: 1000 * 2^1 * jitter = ~2000ms
  ↓ (wait 2 seconds)
Attempt 2: Retry after 2s
  ↓ (fails)
Delay calculation: 1000 * 2^2 * jitter = ~4000ms
  ↓ (wait 4 seconds)
Attempt 3: Final retry after 4s
  ↓ (fails)
Throw final error (maxRetries exhausted)
```

**Total Time:** ~1s + ~2s + ~4s = ~7 seconds for 3 retries

**Why Exponential?**
- Gives API time to recover from overload
- Reduces load during incidents (fewer retries)
- Industry standard (AWS, Google, etc.)

**Why Jitter?**
- Prevents "thundering herd" (many clients retrying simultaneously)
- Distributes retry load over time
- Reduces spike when service recovers

### RetryHandler Class Implementation

**Location:** `src/client/retry-handler.ts`

**Complete Implementation:**
```typescript
export class RetryHandler {
  private config: Required<RetryConfig>;

  constructor(config?: RetryConfig) {
    this.config = {
      maxRetries: config?.maxRetries ?? 3,
      retryDelay: config?.retryDelay ?? 1000,
      exponentialBackoff: config?.exponentialBackoff ?? true
    };
  }

  async executeWithRetry<T>(
    operation: () => Promise<T>,
    operationName: string = 'operation'
  ): Promise<T> {
    let lastError: Error;

    for (let attempt = 0; attempt <= this.config.maxRetries; attempt++) {
      try {
        const result = await operation();

        if (attempt > 0) {
          this.log('info', `Operation succeeded after ${attempt} retries`, { operationName });
        }

        return result;
      } catch (error) {
        lastError = error as Error;

        // Check if we should retry this error
        if (!this.shouldRetry(error, attempt)) {
          throw error;
        }

        // Calculate delay for next retry
        const delay = this.calculateDelay(attempt);

        this.log('debug', `Retry attempt ${attempt + 1}/${this.config.maxRetries}`, {
          operationName,
          delay,
          error: error instanceof Error ? error.message : String(error)
        });

        await this.sleep(delay);
      }
    }

    // All retries exhausted
    this.log('warn', `Max retries exhausted for ${operationName}`, {
      maxRetries: this.config.maxRetries
    });

    throw lastError!;
  }

  private shouldRetry(error: unknown, attempt: number): boolean {
    // Exhausted retries
    if (attempt >= this.config.maxRetries) {
      return false;
    }

    // Type-safe error checking
    if (error instanceof AuthenticationError) {
      return false; // Permanent failure
    }

    if (error instanceof ValidationError) {
      return false; // Permanent failure
    }

    if (error instanceof RateLimitError) {
      return true; // Transient - should retry
    }

    if (error instanceof NetworkError) {
      // Retry on 5xx, timeouts, and network failures
      const status = error.statusCode;

      // No status = network failure (retry)
      if (!status || status === 0) return true;

      // 5xx errors are transient
      if (status >= 500 && status < 600) return true;

      // Timeouts are transient
      if (error.isTimeout) return true;

      // Other status codes are permanent failures
      return false;
    }

    // Unknown error type - default to no retry (conservative)
    return false;
  }

  private calculateDelay(attempt: number): number {
    let delay: number;

    if (this.config.exponentialBackoff) {
      // Exponential: delay * 2^attempt
      delay = this.config.retryDelay * Math.pow(2, attempt);
    } else {
      // Linear: constant delay
      delay = this.config.retryDelay;
    }

    // Add jitter (±10%) to prevent thundering herd
    const jitter = 1 + (Math.random() * 0.2 - 0.1);
    delay = delay * jitter;

    // Cap at 30 seconds
    return Math.min(delay, 30000);
  }

  private async sleep(ms: number): Promise<void> {
    return new Promise(resolve => setTimeout(resolve, ms));
  }

  private log(level: string, message: string, meta?: unknown): void {
    // Simple logging - integrate with BaseClient logger in production
    if (level === 'debug') return; // Skip debug by default

    console[level as 'info' | 'warn' | 'error']?.({
      timestamp: new Date().toISOString(),
      level,
      service: 'RetryHandler',
      message,
      ...meta
    });
  }
}
```

import { describe, it, expect, vi, beforeEach } from 'vitest';
import { RetryHandler } from '../../../src/client/retry-handler';

describe('RetryHandler', () => {

    await vi.runAllTimersAsync();

    const result = await promise;

    expect(result).toBe('success');

    const operation = vi.fn()

    expect(operation).toHaveBeenCalledTimes(1); // No retry
  });

  it('should use exponential backoff delays', async () => {
    const operation = vi.fn()
      .mockRejectedValueOnce(new NetworkError('Error', 500))
      .mockRejectedValueOnce(new NetworkError('Error', 500))
      .mockResolvedValueOnce('success');

    const delays: number[] = [];
    vi.spyOn(global, 'setTimeout').mockImplementation(((callback: () => void, delay: number) => {
      delays.push(delay);
      callback();
      return 0 as any;
    }) as any);

    await handler.executeWithRetry(operation);

    // Verify exponential backoff: ~1000ms, ~2000ms
    expect(delays[0]).toBeGreaterThan(900);

    expect(delays[1]).toBeGreaterThan(1800);

    await expect(handler.executeWithRetry(operation)).rejects.toThrow(finalError);
    expect(operation).toHaveBeenCalledTimes(3); // Initial + 2 retries

### Performance Considerations

**Latency Impact:**
- Retries add latency (exponential backoff can add seconds)
- Total time for 3 retries with default config: ~7 seconds
- Trade-off: Reliability vs. latency

**Best Practices:**
- Set appropriate timeout values (don't retry indefinitely)
- Monitor retry rates (high rates indicate systemic issues)
- Log retry attempts for debugging
- Consider circuit breaker pattern for repeated failures (future enhancement)

**Memory:**
- Minimal memory footprint (no retry state stored)
- Async stack traces preserved in errors

### Troubleshooting Retry Issues

**Common Issues:**

   - Solution: Reduce maxRetries or retryDelay

2. **Retrying Permanent Failures:**
   - Symptom: AuthenticationError being retried

   - Symptom: 500 errors fail immediately
   - Solution: Verify error instanceof NetworkError

4. **Excessive Delay:**
   - Symptom: Long waits between retries

1. ✅ RetryHandler class with generic `executeWithRetry<T>()` method
2. ✅ Configurable retry settings (maxRetries: 3, retryDelay: 1000ms, exponentialBackoff: true)
3. ✅ Intelligent error classification:
   - **Retries:** NetworkError (5xx, timeout, no status), RateLimitError (429)
   - **NO Retry:** AuthenticationError (401/403), ValidationError (400/422), other 4xx
4. ✅ Exponential backoff: `delay = retryDelay * 2^attempt * jitter`
5. ✅ Jitter (±10%) prevents thundering herd
6. ✅ Maximum delay cap of 30 seconds
7. ✅ Full BaseClient integration (all 5 HTTP methods wrapped with retry logic)
8. ✅ Comprehensive testing (26 unit tests + 17 integration tests = 43 tests)

**Technical Decisions:**
1. **Exponential Backoff Default:** Gives APIs time to recover, reduces load during incidents
2. **Jitter Implementation:** Random ±10% variation prevents synchronized retries
3. **Type-Safe Error Classification:** Uses `instanceof` checks for reliable error routing
4. **Transparent Integration:** Retry logic invisible to API modules, wrapped at BaseClient level
5. **Conservative Unknown Errors:** Unknown error types default to no retry (fail-fast)

**Performance:**
- Zero overhead when operations succeed on first attempt
- ~7 seconds total retry time for 3 retries with default 1s delay (exponential)
- Memory efficient: no retry state stored between operations
