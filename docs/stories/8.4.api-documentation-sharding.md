# Story 8.4 - API Documentation Sharding

**Epic**: Epic 8 - Code Quality & Maintainability

## Description (The Why)

The Wildberries API documentation YAML files in `wildberries_api_doc/` are too large for AI agents to process efficiently. Files like `02-products.yaml` (6,615 lines, 41 endpoints), `08-promotion.yaml` (6,873 lines, 41 endpoints), and `11-analytics.yaml` (5,174 lines, 15 endpoints) cause token overflow when agents attempt to read them.

This task requires sharding these large YAML files into smaller, logically organized modules that:
1. Are easy for agents to read without token overflow
2. Maintain logical grouping by functionality
3. Provide clear navigation through index files
4. Preserve all original OpenAPI structure and validity

## Acceptance Criteria

- [ ] Large YAML files (>1000 lines) are sharded into multiple sub-files
- [ ] Each shard file is <1000 lines for agent readability
- [ ] Shards are organized by functional domains (tags/endpoint groups)
- [ ] Index file created in each module directory listing all shards
- [ ] Navigation guide created at `wildberries_api_doc/SHARD_INDEX.md`
- [ ] All OpenAPI references (`$ref`) are resolved and valid
- [ ] Schema components (`components/schemas`) are properly deduplicated
- [ ] Original files preserved in `wildberries_api_doc/original/` backup
- [ ] Testing validation confirms all shards are valid YAML
- [ ] SDK code generation tools can locate endpoints in new structure

## Implementation Plan

### Phase 1: Analysis & Design
1. Analyze large YAML files structure (tags, endpoint groups, schemas)
2. Design sharding strategy per file based on functional domains
3. Create directory structure plan for each module

### Phase 2: Backup & Directory Structure
1. Create `wildberries_api_doc/original/` backup directory
2. Copy all original YAML files to backup
3. Create module subdirectories for sharded files

### Phase 3: Sharding Execution
1. Parse each large YAML file
2. Extract endpoint groups by tags/functional domains
3. Create individual shard files with proper YAML structure
4. Deduplicate and centralize shared schemas
5. Create index files for navigation

### Phase 4: Validation
1. Validate all shard files are valid YAML
2. Verify OpenAPI structure integrity
3. Test navigation and references
4. Create SHARD_INDEX.md master navigation

### Phase 5: Documentation
1. Document the sharding structure
2. Create usage guide for agents
3. Update CLAUDE.md with new paths

### Shard File Format

Each shard file should contain:

```yaml
openapi: 3.0.1
info:
  title: "{Module Name} - {Domain}"
  description: "Extracted from original file for agent processing"
  version: "1.0.0-shard"

servers:
  - url: "{Base URL from original}"

tags:
  - name: "{Domain Name}"
    description: "{Domain description}"

paths:
  /api/path/endpoint1:
    {Full endpoint specification}
  /api/path/endpoint2:
    {Full endpoint specification}

components:
  schemas:
    {Only schemas used by endpoints in this shard}
```

### Index File Format

```yaml
_module: "{Module Name}"
_description: "{Module description}"
_original_file: "{Original filename}"
_base_url: "{Base URL}"
_shards:
  - file: "domain1.yaml"
    domain: "{Domain Name}"
    endpoints: {count}
    description: "{Description}"
  - file: "domain2.yaml"
    domain: "{Domain Name}"
    endpoints: {count}
    description: "{Description}"
_shared_schemas: "_schemas.yaml"
_total_endpoints: {total}
```
