# Story 2.2: Products Module - Product Card CRUD Operations

---

## Status

**Ready for Review**

## Story

**As a** marketplace seller,
**I want** to create, read, update, and delete product cards,
**so that** I can manage my product catalog programmatically.

---

## Acceptance Criteria

1. `createProduct(data: CreateProductRequest)` method creates new product card
2. `getProductCard(productId: string)` method retrieves product details
3. `updateProduct(productId: string, data: UpdateProductRequest)` method updates product card
4. `deleteProduct(productId: string)` method removes product from catalog
5. `listProducts(filters?: ProductFilters)` method retrieves product list with pagination
6. Request/response types include all required fields (brandName, categoryId, characteristics, etc.)
7. Validation error handling for missing required fields with clear error messages
8. Rate limiting enforced (e.g., "1 request per 10 seconds" for product creation)
9. Unit tests cover all CRUD operations with mocked responses
10. Integration tests validate complete product lifecycle (create → read → update → delete)
11. Example code demonstrates creating a complete product with all required fields

### API Specifications

**Base URL**: `https://content-api.wildberries.ru`
[Source: OpenAPI spec wildberries_api_doc/02-products.yaml]

**Endpoints for Story 2.2**:

1. **POST /content/v2/cards/upload** - Create Products
   - Creates product cards with descriptions and characteristics
   - **Request body**: Array of objects with `subjectID` (required) and `variants` array
   - **Async Processing**: Request queued, check error list if 200 OK but some cards fail
   - **Limits**: Max 100 unified cards (imtID), 30 cards each, 10MB max request size
   - **Response**: `{ error: boolean, errorText: string }` - Check error list for failures
   - **Rate limit**: 10 req/min, 6 second interval, 5 burst
   [Source: Line 2792-2990 in 02-products.yaml]

2. **POST /content/v2/get/cards/list** - List Products
   - Returns list of created product cards with filtering and cursor pagination
   - **Request body**: `{ settings: { sort, filter, cursor } }`
   - **Filters**: withPhoto (0/1/-1), textSearch (vendorCode/nmID/barcode), tagIDs, brands, objectIDs, imtID
   - **Pagination**: Cursor-based for >100 products (limit max 100, use updatedAt + nmID for next page)
   - **Response**: `{ cards: ProductCard[], cursor: { total, nmID, updatedAt } }`
   - **Note**: Excludes products in trash
   - **Rate limit**: 100 req/min, 600ms interval, 5 burst
   [Source: Line 1278-1680 in 02-products.yaml]

3. **POST /content/v2/cards/update** - Update Products
   - Updates existing product cards
   - **CRITICAL**: Card completely rewritten - must send ALL parameters (even unchanged)
   - **Request body**: Array of objects (max 3000 cards, 10MB limit)
   - **Required fields**: nmID, vendorCode, sizes (with chrtID for existing sizes)
   - **Cannot edit**: Barcodes, photos, video, tags (use separate endpoints)
   - **Can add**: Additional barcodes to existing products
   - **Response**: `{ error: boolean, errorText: string }` - Check error list for failures
   - **Rate limit**: 10 req/min, 6 second interval, 5 burst
   [Source: Line 1829-2040 in 02-products.yaml]

4. **POST /content/v2/cards/delete/trash** - Delete Products (Soft Delete)
   - Moves product cards to trash (recoverable)
   - **Request body**: `{ nmIDs: number[] }` - Max 1000 nmIDs
   - **Soft Delete**: Cards not permanently deleted, can be recovered
   - **Auto-cleanup**: Cards deleted after 30 days in trash (nightly Moscow time)
   - **Side effect**: New imtID assigned after moving to trash
   - **Response**: `{ data: null, error: boolean, errorText: string }`
   - **Rate limit**: 100 req/min, 600ms interval, 5 burst
   [Source: Line 2146-2238 in 02-products.yaml]

**Authentication**: Bearer token via `Authorization` header (handled by BaseClient)
[Source: OpenAPI spec - security scheme HeaderApiKey]

### Critical Implementation Notes

**1. Product Update Overwrites Entire Card** ⚠️

The update endpoint completely replaces the product card. You MUST send ALL fields, even if only changing one field. Missing fields will be removed from the product.

**Example**:
```typescript
// BAD - Only sends changed field
await updateProduct([{
  nmID: 12345,
  title: 'New Title'  // ERROR: All other fields will be lost!
}]);

// GOOD - Sends all fields
const product = await getProductCard(12345);
await updateProduct([{
  ...product,
  title: 'New Title'  // Only this changes, rest preserved
}]);
```

[Source: Line 1834 in 02-products.yaml - Update method description]

**2. Async Processing for Create/Update**

Product creation and updates are processed asynchronously. A 200 OK response means the request was queued, NOT that products were created successfully. Check the error list endpoint (`/content/v2/cards/error/list`) to verify if any cards failed.

[Source: Line 2800 in 02-products.yaml - Create method description]

**3. Soft Delete Pattern**

`deleteProduct()` moves cards to trash (soft delete). Cards can be recovered using `/content/v2/cards/recover` endpoint. Auto-deletion happens after 30 days in trash.

[Source: Line 2160-2161 in 02-products.yaml - Delete method description]

**4. No Single-Product GET Endpoint**

Wildberries API doesn't provide a GET endpoint for single products. The `getProductCard()` convenience method uses `listProducts()` with a textSearch filter internally.

### Rate Limiting Configuration

**Strict Limits** (Create/Update):
- 10 requests per minute
- 6 second interval between requests
- Burst limit: 5 requests
- **Affects**: createProduct, updateProduct

**Standard Content API Limits** (List/Delete):
- 100 requests per minute
- 600 millisecond interval between requests
- Burst limit: 5 requests
- **Affects**: listProducts, deleteProduct (also getCategories, getCharacteristics from Story 2.1)

**Implementation**:
- BaseClient's RateLimiter enforces limits automatically via rateLimitKey
- Different keys allow independent rate limiting per endpoint
- SDK queues requests when limit exceeded
- Users can catch RateLimitError to implement custom retry logic

### Technical Constraints

**TypeScript**:
- All CRUD request types must have proper required/optional field markings
- Complex nested types (dimensions, sizes, characteristics) must be well-typed
- Generic Promise<T> return types for all async methods

**Validation**:
- Required fields: Validate before API call (throw ValidationError)
- Field length limits: title max 60 chars, vendorCode max 72 chars
- Array limits: Max 100 cards in create, max 3000 in update, max 1000 in delete
- Request size: Max 10MB for create/update requests

**Error Handling**:
- ValidationError for missing required fields (client-side validation)
- RateLimitError for 429 responses (auto-retry by BaseClient)
- AuthenticationError for 401/403 responses
- NetworkError for 5xx responses and timeouts

**Performance**:
- Cursor-based pagination for large product lists (>100 products)
- Batch operations where possible (update 3000 cards, delete 1000 cards)
- Rate limit awareness to avoid API blocks
