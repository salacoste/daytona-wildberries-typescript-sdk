## Story

**As a** marketplace seller,
**I want** to retrieve and respond to customer chat messages,
**so that** I can provide customer support directly through the marketplace.

## Acceptance Criteria

1. Communications module generated from `09-communications.yaml` with type definitions
2. `getChats()` method retrieves all chat conversations (no filtering in API)
3. `getChatEvents(next?: number)` method retrieves chat events with cursor pagination
4. `sendMessage(replySign: string, message?: string, files?: File[])` method sends reply to customer (multipart/form-data)
5. Event polling pattern documented for real-time message monitoring
6. Message content supports text (max 1000 chars) and file attachments (JPEG/PDF/PNG, 5MB each, 30MB total)
7. Event-based architecture properly implemented (single events stream for all chats)
8. `replySign` extraction and usage documented (from Chat or Event with isNewChat=true)
9. Rate limits enforced per endpoint (10 requests/10 seconds)
10. Unit tests validate chat and event retrieval methods
11. Integration tests validate complete chat workflow (get chats → poll events → send message)
12. Example code in `examples/customer-support.ts` demonstrates event-based chat management

### OpenAPI Source

- **Source File**: `wildberries_api_doc/09-communications.yaml`
- **Base URL**: `https://buyer-chat-api.wildberries.ru` (Buyer Chat API domain, NOT feedbacks-api)
- **Get Chats Endpoint**: `GET /api/v1/seller/chats` (no parameters)
- **Get Events Endpoint**: `GET /api/v1/seller/events?next={timestamp}`
- **Send Message Endpoint**: `POST /api/v1/seller/message` (multipart/form-data)
- **Authentication**: Header-based API Key (`Authorization: Bearer <key>`)

### Critical API Architecture Understanding

**EVENT-BASED SYSTEM** (Not Traditional REST):
- ❌ NO per-chat message endpoint like `/chats/{id}/messages`
- ✅ SINGLE events stream for ALL chats via `/api/v1/seller/events`
- ✅ CURSOR pagination using `next` parameter (Unix timestamp with milliseconds)
- ✅ CLIENT-SIDE filtering required to view messages for specific chat

**Chat List Endpoint**:
- `GET /api/v1/seller/chats` returns ALL chats (no filtering parameters)
- Each Chat contains: chatID, replySign, clientID, clientName, goodCard
- replySign from Chat is used for sendMessage()

**Events Endpoint** (Critical for Message Retrieval):
- `GET /api/v1/seller/events?next={timestamp}` returns events for ALL chats
- Cursor pagination: first request without `next`, subsequent with `next` from response
- Response includes: next (cursor for next request), totalEvents, events[]
- Continue pagination while totalEvents > 0
- Each Event contains:
  - chatID, eventID, eventType ('message')
  - isNewChat (boolean) - if true, event includes replySign
  - message: { text, attachments: { files, images, goodCard } }
  - sender: 'client' | 'seller' | 'wb'
  - addTimestamp (Unix with ms), addTime (RFC 3339)
  - replySign (ONLY when isNewChat=true)
  - clientID, clientName

**Send Message Endpoint** (Multipart Form Data):
- `POST /api/v1/seller/message`
- Content-Type: `multipart/form-data`
- Required field: `replySign` (string, max 255 chars)
- Optional field: `message` (string, max 1000 chars)
- Optional field: `file` (binary[], JPEG/PDF/PNG, 5MB each, 30MB total)
- At least one of message or file must be provided
- Returns: MessageResponse with result{ addTime (number), chatID (string) }

### Module Architecture

**replySign Critical Understanding**:
- **Purpose**: Unique signature required to send message to a chat
- **Source 1**: `Chat.replySign` from `getChats()` - always available for each chat
- **Source 2**: `Event.replySign` from `getChatEvents()` - ONLY when `isNewChat: true`
- **Usage**: First parameter of `sendMessage()` method
- **Implementation**: Developer must map chatID to replySign using Chat list or new chat events

**Event-Based Message Flow**:
1. Fetch all chats to get chatID → replySign mapping
2. Poll events to get new messages for ALL chats
3. Filter events by chatID if viewing specific conversation (client-side)
4. For new chats (isNewChat=true), extract replySign from event
5. Send message using replySign (from Chat or new chat event)

**Cursor Pagination Pattern**:
```typescript
let cursor: number | undefined = undefined;

do {
  const response = await getChatEvents(cursor);
  const { events, totalEvents, next } = response.result;

  // Process events...
  processEvents(events);

  // Update cursor for next iteration
  cursor = totalEvents > 0 ? next : undefined;
} while (cursor !== undefined);
```

**File Upload Pattern** (Multipart Form Data):
```typescript
const formData = new FormData();
formData.append('replySign', replySign);
formData.append('message', 'Response text');
files.forEach(file => formData.append('file', file));

await axios.post(url, formData, {
  headers: { 'Content-Type': 'multipart/form-data' }
});
```

### Event Processing Patterns

**Typical Event Monitoring Workflow**:
1. **Initial Setup**: Fetch all chats to build chatID → replySign map
2. **Event Polling Loop**:
   - Fetch events with current cursor
   - Process new events (filter by sender, chatID as needed)
   - Update cursor with next value
   - Repeat until totalEvents = 0, then wait interval and start new poll
3. **Message Response**:
   - Extract replySign (from Chat map or new chat event)
   - Prepare message (text and/or files)
   - Send using sendMessage()

**Event Filtering** (Client-Side):
```typescript
// Get messages for specific chat
const chatMessages = events.filter(e => e.chatID === targetChatID);

// Get only customer messages
const customerMessages = events.filter(e => e.sender === 'client');

// Get only new chats
const newChats = events.filter(e => e.isNewChat);
```

**File Attachment Handling**:
- **Customer Files**: Event.message.attachments.files[] - download using Event.message.attachments.files[].url
- **Customer Images**: Event.message.attachments.images[] - display using Event.message.attachments.images[].url
- **Order Context**: Event.message.attachments.goodCard - order details attached to message
- **Seller Upload**: Create File/Blob objects and pass to sendMessage()

**Message Validation**:
- replySign: Required, non-empty string, max 255 characters
- message: Optional, max 1000 characters
- files: Optional, JPEG/PDF/PNG only, 5MB per file, 30MB total
- At least one of message or files must be provided

**Polling Best Practices**:
- Minimum interval: 10 seconds (matches rate limit)
- Track cursor persistence across polling cycles
- Handle errors gracefully (continue polling on transient errors)
- Implement graceful shutdown (clear interval on stop)
- Consider exponential backoff on repeated errors
- Log polling activity for debugging and monitoring
