## Dev Notes

### Error Hierarchy Architecture

**Error Model:** Typed Error Hierarchy with Rich Context

**Exception Hierarchy:**
```
Error (native JavaScript)
  └── WBAPIError (base SDK error)
        ├── AuthenticationError (401, 403)
        ├── RateLimitError (429)
        ├── ValidationError (400, 422)
        └── NetworkError (timeouts, 5xx)
```

**Error Propagation Strategy:** Fail-fast with typed exceptions

All SDK errors should extend WBAPIError to enable consumers to catch all SDK-specific errors with a single catch block if desired.

[Source: architecture.md#Error Handling Strategy]

### WBAPIError Base Class Specification

**Properties:**
- `message: string` - Error message (inherited from Error)
- `statusCode?: number` - HTTP status code if applicable
- `response?: unknown` - API response body if available
- `requestId?: string` - Correlation ID for debugging
- `name: string` - Error class name

**Method:**
- `getUserMessage(): string` - Human-readable message with recovery guidance

**Implementation Notes:**
- Must call `super(message)` to properly extend Error
- Use `Error.captureStackTrace(this, this.constructor)` to preserve stack trace
- Set `this.name = this.constructor.name` for proper error identification
- Override `getUserMessage()` in subclasses for specific recovery guidance

[Source: architecture.md#Error Handling Strategy]

### AuthenticationError Specification

**Triggered On:** 401 Unauthorized, 403 Forbidden, invalid API key validation

**Properties:**
- Inherits all WBAPIError properties
- `statusCode: 401 | 403`

**Recovery Guidance:**
- "Verify your API key is valid and correctly formatted"
- "Check that your API key has the required permissions for this operation"
- "Ensure the Authorization header is properly set"

**Usage Example:**
```typescript
try {
  await sdk.products.createProduct(data);
} catch (error) {
  if (error instanceof AuthenticationError) {
    console.error('Auth failed:', error.getUserMessage());
    // Prompt user to update API key
  }
}
```

[Source: architecture.md#Error Handling Strategy]

### RateLimitError Specification

**Triggered On:** 429 Too Many Requests

**Properties:**
- Inherits all WBAPIError properties
- `statusCode: 429`
- `retryAfter: number` - Milliseconds until retry is allowed

**Recovery Guidance:**
- "Rate limit exceeded. The SDK will automatically retry this request after {retryAfter}ms"
- "If this happens frequently, consider implementing request batching or caching"

**Important:** SDK's RetryHandler will automatically retry 429 errors, so consumers typically don't need to handle this manually.

[Source: architecture.md#Error Handling Strategy]

### ValidationError Specification

**Triggered On:** 400 Bad Request, 422 Unprocessable Entity

**Properties:**
- Inherits all WBAPIError properties
- `statusCode: 400 | 422`
- `fieldErrors?: Record<string, string>` - Map of field name to error message

**Recovery Guidance:**
- "Validation failed. Check the following fields: {list of field errors}"
- "Ensure all required fields are provided and meet the API specifications"

**Field Errors Format:**
```typescript
{
  brandName: "Brand name is required",
  price: "Price must be a positive number",
  categoryId: "Invalid category ID"
}
```

[Source: architecture.md#Error Handling Strategy]

### NetworkError Specification

**Triggered On:** Timeouts, connection failures, 500-level server errors

**Properties:**
- Inherits all WBAPIError properties
- `statusCode: 0 | 500 | 502 | 503 | 504` (0 for network failures)
- `cause?: Error` - Original error from HTTP client
- `isTimeout: boolean` - True if error was caused by timeout

**Recovery Guidance:**
- If timeout: "Request timed out after 30 seconds. The SDK will automatically retry (attempt {n} of 3)"
- If 5xx: "Server error occurred. The SDK will automatically retry (attempt {n} of 3)"
- If network failure: "Network connection failed. Please check your internet connection"

**Important:** SDK's RetryHandler automatically retries NetworkErrors (max 3 attempts with exponential backoff).

[Source: architecture.md#Error Handling Strategy]

### Coding Standards for Error Classes

**Naming Conventions:**
- Class names: PascalCase ending in "Error" (e.g., `AuthenticationError`)
- Files: kebab-case (e.g., `auth-error.ts`)
- Properties: camelCase (e.g., `retryAfter`, `fieldErrors`)

**TypeScript Rules:**
- Enable strict mode (already configured in tsconfig.json)
- No `any` types - use `unknown` for response property
- All properties must have explicit types
- Use readonly for properties that shouldn't be modified after construction

**JSDoc Requirements:**
- Class-level JSDoc with description and @example
- Property documentation with @property tags
- Method documentation with @returns and @example
- Examples must show realistic usage with try-catch

**Example JSDoc:**
```typescript
/**
 * Authentication error thrown when API key is invalid or lacks permissions.
 *
 * @example

 *     console.error('Invalid API key:', error.getUserMessage());
 *   }
 * }
 * ```
 */
export class AuthenticationError extends WBAPIError {
  /**
   * Creates an authentication error
   * @param message - Error message
   * @param statusCode - HTTP status code (401 or 403)
   */
  constructor(message: string, statusCode: 401 | 403 = 401) {
    // implementation
  }
}
```

### Error Message Guidelines

**Developer-Friendly Principles:**
1. Be specific about what went wrong
2. Provide actionable recovery steps
3. Avoid technical jargon where possible
4. Never expose sensitive information (API keys, tokens, PII)
5. Include context (field names, expected formats, retry attempts)

**Good Error Message:**
```
"Authentication failed. Please verify your API key is valid and has the required permissions. Check that the Authorization header is properly set."
```

**Bad Error Message:**
```
"Error 401"
```

**Security Note:** Error messages should NEVER include:
- Full API keys (can show first 4 characters: "API key starting with 'sk_1234...'")
- Request/response bodies with sensitive data
- Internal system paths or stack traces in production
